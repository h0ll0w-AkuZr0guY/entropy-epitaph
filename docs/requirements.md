# 产品需求与验收标准 / Requirements & Acceptance Criteria

## MVP 功能需求

### 墓碑
- 支持 `code / relic / link / nameless` 四类创建。
- 支持 `css / canvas / ascii / random`；随机值在创建后解析并锁定。
- 保存原文、当前损坏文本、墓志铭、熵值、阶段、随机种子和类型元数据。
- 个人列表按创建时间倒序，可按类型、阶段和风格筛选并分页展示。

### 熵增
- 后端使用真实时间差计算，不为每块碑建立独立定时器。
- 正常模式调度间隔 5 分钟；演示模式 30 秒，倍率 ×720。
- 阶段阈值必须由熵值推导；达到 1.0 时仅生成一张凭证。
- 凭证以普通碑平均衰变率的 3 倍继续衰变。

### 互动
- 每用户、每碑、每天最多擦拭一次；重复请求返回 429。
- 公共碑允许凭吊；每 IP/浏览器、每碑、每天一次，总延寿上限 0.15。
- 公共响应不得包含 `user_id`、`title`、`original_content`，可见正文需截断并遮蔽。

### AI 与外部服务
- AI 覆盖墓志铭、阶段损坏文本、链接摘要、无名低语和最终墓前词。
- API key 缺失、超时或网络失败时必须使用本地 fallback，不阻断演示。
- Wayback 查询超时不得阻断链接碑创建。

## 演示数据需求

- 数量允许 50–200，仓库标准 fixture 固定为 120。
- 120 条必须形成 `4 类型 × 5 阶段 × 3 风格 × 2 事例`。
- 至少包含公开/私有、存活/寂灭、可见/已归档凭证、不同语言代码和不同时间。
- 数据必须可复现、可校验、可幂等灌入 SQLite，且不能删除真实用户数据。

## 双运行模式

| 能力 | FastAPI 本地模式 | GitHub Pages 静态模式 |
|---|---|---|
| 初始 120 条数据 | SQLite | JSON fixture |
| 时间衰变 | APScheduler | 浏览器读取时计算 |
| 持久化 | SQLite | localStorage |
| AI / Wayback | 可实时调用，有 fallback | 只使用预制/fallback 内容 |
| 多访客共享 | 可由统一后端实现 | 不支持 |
| 凭吊限流 | IP + 日期 | 浏览器 + 日期 |

## 非功能需求

- Pages 项目子路径下资源与 fixture 不得 404。
- 静态构建不得请求 `localhost:8000`。
- 120 条数据下首屏只渲染 36 张卡片，避免 Canvas 重绘过载。
- API key 和本地数据库不得进入 Git。
- GitHub Actions 必须执行 fixture 校验、Python 测试、前端单测、构建和浏览器冒烟测试。

## 验收标准

1. fixture 校验报告显示：类型各 30、阶段各 24、风格各 40、公开 75、寂灭 12、凭证 12。
2. `/monuments/my` 在展示模式返回 120 条；公共区返回 75 条；档案有可见条目。
3. 擦拭首次成功、同日第二次返回 429；公开接口无私有字段。
4. Pages 浏览器测试可完成查看、筛选、创建、刷新持久化、公共区和档案浏览。
5. Pages bundle 不包含本机 API 地址，并使用 `/<repository>/` base path。
